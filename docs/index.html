PdfUtil

A .NET 8 library that protects and unprotects PDF files, changes their passwords and document information, checks passwords, and reads document details down to fonts, images, form fields and signatures. It also validates and repairs damaged files, removes scripts and other unwanted content, and manages attachments. It works with every PDF version from 1.0 to 2.0, and every file it writes opens in all major viewers.

Tutorial

Set up a project

This tutorial takes about 15 minutes. You will create a console app, protect a PDF, check passwords, read metadata and handle the common error cases. Every code sample was compiled and run against the library, and the output shown is real.

Create a console app and reference PdfUtil:

Shell
dotnet new console -n PdfDemo
cd PdfDemo
dotnet add reference ../src/PdfUtil/PdfUtil.csproj

You need a PDF to work with. Any PDF will do. If you don't have one, the sample app can write one for you:

Shell
dotnet run --project ../samples/PdfUtil.Sample -- demo ./samples
cp ./samples/source.pdf ./report.pdf

Protect a PDF

Replace Program.cs with:

C#
using PdfUtil;

var result = Pdf.Protect("report.pdf", "report-protected.pdf", new PdfProtectionOptions
{
    UserPassword  = "open-sesame",   // needed to open the file
    OwnerPassword = "full-access",   // grants all permissions
});

Console.WriteLine($"PDF {result.SourceVersion} -> {result.OutputVersion}, {result.Algorithm} (R{result.Revision})");
foreach (var warning in result.Warnings)
    Console.WriteLine("warning: " + warning);
Output
PDF 1.4 -> 1.7, Aes256 (R6)

What happened:

  • The file was encrypted with AES-256, the default and strongest algorithm.
  • The version was raised from 1.4 to 1.7, because AES-256 needs PDF 1.7 with Adobe extension level 8. PdfUtil never lowers a version.
  • The output was verified, and only then moved into place as report-protected.pdf.

Open report-protected.pdf in any viewer. It asks for a password, and open-sesame opens it.

The input and output paths may be the same file. PdfUtil writes to a temporary file in the same folder and replaces the original atomically, so a failure never leaves a half-written file.

Set permissions

By default, someone who opens the file with the user password may do everything. Restrict that with Permissions:

C#
var options = new PdfProtectionOptions
{
    UserPassword  = "open-sesame",
    OwnerPassword = "full-access",
    Permissions   = PdfPermissions.Print
                  | PdfPermissions.PrintHighQuality
                  | PdfPermissions.ExtractForAccessibility,
};
Pdf.Protect("report.pdf", "report-protected.pdf", options);

Users who open the file with open-sesame can print it and screen readers can read it, but copying and editing are blocked. The owner password lifts all restrictions.

Permissions are honoured by viewers, not enforced by cryptography. Anyone who can open the file can technically decrypt it. Use the user password to keep content private; use permissions to express intent.

A common variation is to leave UserPassword empty. The file then opens without a password, but the permissions still apply. If you leave OwnerPassword empty instead, PdfUtil generates a random owner password and discards it, so the permissions can never be lifted.

Check a password

C#
var check = Pdf.VerifyPassword("report-protected.pdf", "open-sesame");
Console.WriteLine($"{check.IsValid} {check.MatchedAs}");

var wrong = Pdf.VerifyPassword("report-protected.pdf", "guess");
Console.WriteLine($"{wrong.IsValid} {wrong.MatchedAs}");
Output
True User
False None

A wrong password is a normal result, not an exception. MatchedAs tells you which password matched: User, Owner or None. If the same text is both passwords, it reports Owner.

Use Pdf.IsEncrypted(path) when you only need to know whether a file is protected at all, and check.OpensWithoutPassword to detect files that are encrypted only to enforce permissions.

Handle errors

All library exceptions derive from PdfUtilException, and their messages never contain passwords. These are the ones you will meet in practice:

C#
try
{
    Pdf.Protect("report.pdf", "report-protected.pdf", options);
}
catch (PdfComplianceException ex)        // the input is PDF/A, which forbids encryption
{
    Console.WriteLine(ex.Message);
}
catch (PdfAlreadyEncryptedException)       // the input is already protected (see step 7)
{
}
catch (PdfPasswordEncodingException ex)    // the password can't be used safely with this algorithm
{
    Console.WriteLine(ex.Message);
}
catch (PdfCorruptException ex)            // not a PDF, or damaged beyond repair
{
    Console.WriteLine(ex.Message);
}

For PDF/A input you can choose to encrypt anyway. The output is then no longer PDF/A conformant, and a warning says so:

C#
options.PdfAPolicy = PdfAPolicy.Proceed;

Damaged files are repaired automatically when possible (broken cross-reference tables, wrong offsets, wrong stream lengths, junk before the header). The repair is reported in result.Warnings and info.WasRepaired.

Re-encrypt a protected file

By default PdfUtil refuses to protect a file that is already encrypted. To change the passwords or the algorithm, opt in and supply the current owner password:

C#
var reEncrypt = new PdfProtectionOptions
{
    UserPassword           = "new-password",
    OwnerPassword          = "new-owner",
    AlreadyEncryptedPolicy = AlreadyEncryptedPolicy.ReEncryptWithOwnerPassword,
    CurrentOwnerPassword   = "full-access",
};
Pdf.Protect("report-protected.pdf", "report-protected.pdf", reEncrypt);

Console.WriteLine(Pdf.VerifyPassword("report-protected.pdf", "new-password").MatchedAs);
Output
User

The user password is not enough; re-encryption requires the owner password. The document content and its permanent ID are preserved byte for byte.

Async, streams and limits

The static Pdf class is convenient for scripts and tools. In services, use the async classes directly. They take a CancellationToken, and a PdfUtilOptions object for limits and logging:

C#
IPdfProtector protector = new PdfProtector(new PdfUtilOptions
{
    MaxFileSizeBytes = 200 * 1024 * 1024,
    Logger = (level, message) => Console.WriteLine($"[{level}] {message}"),
});

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
await using var input  = File.OpenRead("report.pdf");
await using var output = File.Create("report-protected.pdf");
var result = await protector.ProtectAsync(input, output, options, cts.Token);
Output
[Information] Protecting a 722-byte document with Aes256.
[Information] The input has no valid /ID; a new permanent identifier was generated.
[Information] Protected output passed self-verification.
  • ProtectAsync writes nothing to output until the protected document has passed verification. If verification fails, the stream stays empty.
  • Input streams don't need to be seekable. Network or HTTP request streams are buffered in memory, or in a temporary file above 32 MiB.
  • The services are stateless and thread-safe. Create one instance and share it.

To work fully in memory, use the byte-array overload:

C#
byte[] pdfBytes = File.ReadAllBytes("report.pdf");
byte[] protectedBytes = Pdf.Protect(pdfBytes, options, out var result);

Dependency injection

Add the extension package, then register the services:

C#
using PdfUtil.Extensions.DependencyInjection;

builder.Services.AddLogging();
builder.Services.AddPdfUtil(o => o.MaxDecompressedStreamBytes = 64 * 1024 * 1024);

Then inject IPdfProtector, IPdfEditor, IPdfOpener, IPdfInspector or IPdfBatchProcessor wherever you need them. All of them are singletons.

C#
public sealed class ReportService
{
    private readonly IPdfProtector _protector;
    private readonly IPdfInspector _inspector;

    public ReportService(IPdfProtector protector, IPdfInspector inspector)
    {
        _protector = protector;
        _inspector = inspector;
    }

    public async Task<int?> ProtectAsync(Stream pdf, Stream destination, string password, CancellationToken ct)
    {
        await _protector.ProtectAsync(pdf, destination, new PdfProtectionOptions { UserPassword = password }, ct);
        destination.Position = 0;
        var info = await _inspector.GetInfoAsync(destination, password, ct);
        return info.PageCount;
    }
}

When an ILoggerFactory is registered, library log messages go to an ILogger with the category PdfUtil. They never contain passwords, keys or document content.

Guides

Choosing an algorithm

AlgorithmHandlerOutput versionOpens in
Aes256 (default)V5 / R6At least 1.7 with Adobe extension level 8, or 2.0 when the source is 2.0All current browsers (Chrome, Edge, Firefox, Safari), Acrobat Reader X and later, Foxit, SumatraPDF, macOS Preview, iOS and Android viewers, qpdf, mutool
Aes128V4 / R4At least 1.6Everything above, plus readers from about 2005 (Acrobat 7–9)
Rc4_128V2 / R3At least 1.4Practically every reader ever made. RC4 is cryptographically weak.

Use Aes256 unless you know your readers are older than about 2008 (for example Acrobat 8 or earlier). Then use Aes128, and Rc4_128 only for the very oldest.

The output version is the higher of the source version and the version the algorithm needs. It is never lowered, and a catalog /Version entry is kept consistent with the header.

Password rules

PdfUtil's main promise is that the password you set always opens the file, in every viewer. Real viewers turn passwords into bytes in different ways, so by default PdfUtil only accepts passwords that every major viewer handles identically.

AES-256AES-128 / RC4-128
Accepted by default (PasswordPolicy.Interoperable)Latin letters without accents, digits, punctuation, Cyrillic, Greek, Chinese and Japanese ideographs, Arabic, HebrewPrintable ASCII only
Rejected by defaultAccented letters (é, ü), Korean Hangul, emoji, non-ASCII spaces, ligaturesAny non-ASCII character, such as é or €
Maximum length127 bytes of UTF-8; longer passwords are truncated the same way when protecting and verifying32 bytes; longer passwords are rejected unless AllowPasswordTruncation = true

Why the default is strict

Automated tests against real viewers found these differences:

  • AES-128 and RC4: the specification says PDFDocEncoding, Firefox (pdf.js) effectively uses Latin-1, and Apple's viewers (Safari, Preview, iOS) use UTF-8. A password with é or € opens in some viewers and is rejected in others.
  • AES-256: Apple's viewers mishandle accented letters and emoji, even though the specification defines how they should be encoded.

Using the specification rules instead

If you only target specification-compliant readers such as Acrobat, you can apply the ISO rules exactly:

C#
var options = new PdfProtectionOptions
{
    UserPassword   = "Café-Ångström",
    OwnerPassword  = "full-access",
    PasswordPolicy = PdfPasswordPolicy.Specification,
};

Under this policy, AES-256 passwords are prepared with SASLprep (RFC 4013), so é typed as one character or as e plus a combining accent gives the same key. AES-128 and RC4 accept all of PDFDocEncoding. When SASLprep changes a password, result.UserPasswordWasNormalized is true and a warning is added.

Rules that always apply

  • Passwords are never trimmed or case-folded: "Secret " and "secret" are different passwords.
  • The empty user password is allowed. The document then opens without a password.
  • When verifying files made by other tools, PdfUtil also tries the encodings those tools use, so passwords created elsewhere still verify.

What the output looks like

By default, every operation rewrites the whole file in the most compatible form PDF allows (see Smaller files and incremental saves for the alternatives):

  • A %PDF-x.y header followed by a binary comment line.
  • Plain objects only: no object streams and no cross-reference stream.
  • One classic cross-reference table with exactly 20-byte entries, then a single trailer with /Size, /Root, /Info, /ID and /Encrypt.

Content is preserved byte for byte. Every page, font, image, annotation, form field, bookmark and attachment survives. Streams are never recompressed; only string and stream encryption is added, and each stream's /Length is updated. Object numbers are kept.

A few things are deliberately left out: the linearization ("fast web view") dictionary and hint tables, old cross-reference streams, and object-stream containers. Stale linearization hints break browsers, so the output never claims to be linearized.

Self-verification

Before the output reaches you, PdfUtil re-reads it in strict mode, with no repair allowed, and checks that:

  • the user password opens it as User, the owner password as Owner, and a wrong password fails;
  • every cross-reference offset is exact and the /Encrypt dictionary is exactly as specified;
  • /ID[0] equals the bytes used to derive the encryption key;
  • every object decrypts to exactly the intended object, every stream decrypts to the source bytes, and compressed streams still decompress;
  • the page count, page sizes, Info dictionary and XMP metadata match the source.

If any check fails, you get PdfVerificationException and no output.

The trailer /ID

A PDF's trailer holds two identifiers: a permanent one, /ID[0], and a changing one, /ID[1]. For AES-128 and RC4, /ID[0] is part of the encryption key, so getting it wrong makes the file impossible to open. PdfUtil guarantees that:

  • The IDs are handled as raw bytes and never as text. IDs that happen to start with FE FF or EF BB BF, or that contain 00, \, parentheses or line breaks, are kept exactly. Any length is accepted.
  • /ID[0] is preserved byte for byte. If it is missing or malformed, which is common in PDF 1.0–1.3 files, 16 random bytes are generated.
  • /ID[0] is fixed before the key is derived, and the exact same bytes are written to the output.
  • /ID[1] is regenerated on every save and never used for the key.
  • For files with incremental updates, the ID from the last update is used.
  • Both IDs are written as hex strings and never encrypted.

Read them with info.PermanentId and info.ChangingId (byte[]), or with info.PermanentIdHex and info.ChangingIdHex.

Changing document information

You can change the title, author and other document information in the same step as protecting. Set InfoChanges; any property you leave null keeps its current value.

C#
var options = new PdfProtectionOptions
{
    UserPassword  = "open-sesame",
    OwnerPassword = "full-access",
    InfoChanges   = new PdfInfoChanges
    {
        Title  = "Quarterly report",
        Author = "Finance team",
        UpdateModificationDate = true,
    },
};
options.InfoChanges.CustomProperties["Department"] = "Finance";
options.InfoChanges.Remove.Add("Keywords");

var result = Pdf.Protect("report.pdf", "report-protected.pdf", options);
Console.WriteLine($"{result.DocumentInfoChanged} {result.XmpUpdated}");
Output
True False

XmpUpdated is False here because the sample file has no XMP metadata. When a document has XMP, PdfUtil updates the matching XMP properties too. Many viewers show XMP values in preference to the Info dictionary, so updating both keeps them consistent.

Removing and changing protection

Once a document is protected, IPdfEditor can remove the protection, change it, or change the document information while keeping it. Every edit goes through the same self-verification as protection, and file output is replaced atomically.

C#
// Remove protection (needs the owner password)
var unlocked = Pdf.Decrypt("report-protected.pdf", "report-unlocked.pdf", "o-pass");
Console.WriteLine($"Encrypted: {unlocked.IsEncrypted}");

// Change the password to open and the permissions; everything else is kept
var changed = Pdf.ChangeSecurity("report-protected.pdf", "report-new-password.pdf", new PdfSecurityChanges
{
    CurrentOwnerPassword = "o-pass",
    UserPassword         = "new-password",
    Permissions          = PdfPermissions.Print,
});
Console.WriteLine($"{changed.Algorithm} (R{changed.Revision})");

// Rename the document and keep the protection exactly as it is
var edited = Pdf.EditInfo("report-protected.pdf", "report-renamed.pdf", new PdfInfoChanges { Title = "Q3 report (final)" }, "o-pass");
Console.WriteLine($"Still protected: {edited.IsEncrypted} ({edited.Algorithm})");
Console.WriteLine(Pdf.VerifyPassword("report-renamed.pdf", "u-pass").MatchedAs);
Output
Encrypted: False
Aes256 (R6)
Still protected: True (Aes256)
User

The last line shows something worth knowing: after EditInfo, the original password to open (u-pass) still works, although it was never supplied. PdfUtil keeps the document's encryption dictionary and file key unchanged, so every password and permission stays the same.

OperationNeedsOutput
DecryptThe owner password, or the password to open with AllowUserPassword = trueNot encrypted
ChangeSecurityThe owner passwordNew settings; anything left null is kept
EditInfoThe owner password for protected filesSame protection as before

What can be kept when changing security

  • Owner password, permissions, algorithm and metadata encryption are kept. RC4 40-bit and AES-256 revision 5, which PdfUtil doesn't write, are upgraded with a warning.
  • The password to open is recovered from the owner password and kept for RC4 and AES-128 files. AES-256 is designed so that it can't be recovered, so for AES-256 files it is kept only when it is empty; otherwise set UserPassword.

Why removing protection needs the owner password. Removing protection also removes the owner's restrictions. The password to open is only enough when you set AllowUserPassword, and you should only do that when the person is entitled to an unrestricted copy.

Batch processing and progress

IPdfBatchProcessor runs an operation over many documents in parallel. A file that fails never stops the others unless you set StopOnFirstError.

C#
IPdfBatchProcessor batch = new PdfBatchProcessor();
var jobs = new[] { "report-unlocked.pdf", "not-a-pdf.pdf" }
    .Select(f => new PdfFileJob(f, Path.ChangeExtension(f, ".secured.pdf")));
var results = await batch.ProtectFilesAsync(jobs,
    new PdfProtectionOptions { UserPassword = "open-sesame", OwnerPassword = "full-access" },
    new PdfBatchOptions { MaxDegreeOfParallelism = 4 });
Console.WriteLine($"{results.Succeeded} succeeded, {results.Failed} failed");
foreach (var item in results.Items.Where(i => i.Status == PdfBatchItemStatus.Failed))
    Console.WriteLine($"{item.Item.InputPath}: {item.Error!.Message}");
Output
1 succeeded, 1 failed
not-a-pdf.pdf: The input is not a PDF file: no '%PDF-' header was found in the first 1024 bytes.

Besides ProtectFilesAsync there are DecryptFilesAsync, InspectFilesAsync, VerifyPasswordFilesAsync, and RunAsync for any operation of your own. Results come back in input order with status, result, error, warnings and duration.

Fonts, images, forms and more

Pdf.Inspect (or IPdfAnalyzer.InspectAsync) returns everything GetInfo returns, plus details that need a walk through the whole document: fonts, images, attachments, bookmarks, form fields, signatures, page labels and actions. By default it collects all of them.

C#
var info = Pdf.Inspect("report.pdf");
foreach (var font in info.Fonts)
    Console.WriteLine($"Font: {font.Name} ({font.Subtype}), embedded: {font.IsEmbedded}");
foreach (var bookmark in info.Bookmarks)
    Console.WriteLine($"Bookmark: {bookmark.Title} -> page {bookmark.Page}");
foreach (var field in info.FormFields)
    Console.WriteLine($"Field: {field.FullName} ({field.Type}) = {field.Value}");
Console.WriteLine($"Page labels: {string.Join(", ", info.PageLabels)}");
Console.WriteLine($"JavaScript: {info.HasJavaScript} ({string.Join(", ", info.JavaScriptNames)})");
Output
Font: Helvetica (Type1), embedded: False
Bookmark: Introduction -> page 2
Field: name (Text) = Jane
Page labels: i, 1
JavaScript: True (init)

On large files, ask only for what you need. GetInfo collects none of these details, so it stays fast.

C#
var quick = Pdf.Inspect("report.pdf", new PdfInspectionOptions
{

Repairing a damaged file

Pdf.Repair (or IPdfCleaner.RepairAsync) writes a clean, single-revision copy of a damaged file, and tells you exactly what it fixed.

C#
var result = Pdf.Repair("damaged.pdf", "repaired.pdf");
foreach (var repair in result.Repairs)
    Console.WriteLine(repair);
Console.WriteLine($"Pages: {result.PageCount}, may be missing: {result.PagesMayBeMissing}");
Console.WriteLine($"Valid now: {Pdf.Validate("repaired.pdf").IsValid}");
Output
Rebuilt the damaged cross-reference information by scanning the file.
Pages: 2, may be missing: False
Valid now: True

What gets repaired

  • File structure: rebuilt cross-reference data, corrected offsets and stream lengths, data before the header, loops in the revision chain.
  • Page tree: wrong /Count and /Parent entries, repeated or invalid entries, and pages without a /MediaBox (they get the US Letter size readers assume).
  • References to objects that don't exist are removed.
  • Normalization: incremental updates are merged, object streams and cross-reference streams become a classic table, linearization is removed and unused objects are dropped.

Pages are never dropped silently. If the page tree declares more pages than can be read, or page objects sit outside the page tree, PagesMayBeMissing is set and a warning says how many. DeclaredPageCount, PageCount and OrphanedPageCount give the numbers.

Streams are copied byte for byte; a damaged compressed stream is kept as it is. Protected files keep exactly the same security:

C#
// Keep the protection exactly as it is (needs the owner password)...
Pdf.Repair("damaged-protected.pdf", "repaired-protected.pdf", new PdfRepairOptions { Password = "owner" });

// ...or write the repaired copy without protection.
Pdf.Repair("damaged-protected.pdf", "repaired-open.pdf", new PdfRepairOptions { Password = "owner", RemoveProtection = true });

Smaller files and incremental saves

Two options change how a PDF is written. Both are off by default, because the default layout opens in every reader ever made.

Smaller files with object streams

Every operation that writes a PDF takes a Write option. With UseObjectStreams, objects are packed into compressed object streams and the cross-reference table becomes a compressed cross-reference stream.

C#
var classic = Pdf.Protect("book.pdf", "book-classic.pdf", new PdfProtectionOptions { UserPassword = "open-sesame" });
var small = Pdf.Protect("book.pdf", "book-small.pdf", new PdfProtectionOptions
{
    UserPassword = "open-sesame",
    Write = new PdfWriteOptions { UseObjectStreams = true },
});
Console.WriteLine($"Classic:    {new FileInfo("book-classic.pdf").Length,7:N0} bytes (PDF {classic.OutputVersion})");
Console.WriteLine($"Compressed: {new FileInfo("book-small.pdf").Length,7:N0} bytes (PDF {small.OutputVersion})");
Output
Classic:     99,707 bytes (PDF 1.7)
Compressed:  30,820 bytes (PDF 1.7)

This 200-page file shrinks by about 70%; files whose size is mostly images or fonts shrink less. Object streams need PDF 1.5, so the version is raised to at least 1.5, and readers older than about 2003 (Acrobat 5) can't open such files.

Encryption follows ISO 32000: an object stream is encrypted as a whole, the cross-reference stream is never encrypted, and signature dictionaries and the encryption dictionary are never packed. Self-verification checks the packed layout like any other output.

Incremental saves

EditInfo, AddAttachment and RemoveAttachment can append their change to the end of the file instead of rewriting it. Every original byte stays exactly where it was.

C#
var result = Pdf.EditInfo("report.pdf", "report-edited.pdf", new PdfEditInfoOptions
{
    Changes = new PdfInfoChanges { Title = "Q3 report (final)" },
    SaveMode = PdfSaveMode.Incremental,
});
var original = File.ReadAllBytes("report.pdf");
var edited = File.ReadAllBytes("report-edited.pdf");
Console.WriteLine($"Saved as: {result.SaveMode}");
Console.WriteLine($"Original bytes unchanged: {edited.AsSpan(0, original.Length).SequenceEqual(original)}");
Console.WriteLine($"Appended: {edited.Length - original.Length} bytes");
Console.WriteLine($"Revisions: {Pdf.GetInfo("report-edited.pdf").IncrementalUpdateCount + 1}");
Output
Saved as: Incremental
Original bytes unchanged: True
Appended: 249 bytes
Revisions: 2
  • How it's written: the changed and new objects, a cross-reference section in the same style as the source (table or stream), /Prev pointing at the previous section, the same /ID[0] and a new /ID[1].
  • Verified: the original bytes are compared, every appended object is read back, and every other object must still come from the original revision.
  • Signatures: the signed bytes stay intact, so each signature still covers exactly what was signed. Viewers will show that the document was changed after signing.
  • Versions: the header is part of the original bytes, so a required version increase goes into the catalog's /Version.

Nothing is really removed. An incremental update only adds. A removed attachment or an old title stays readable in the earlier revision, so removing an attachment incrementally adds a warning, and sanitizing is always a full rewrite. Use the default Rewrite mode when content must be gone.

Incremental saves are only possible for unencrypted documents whose cross-reference data is intact; otherwise you get NotSupportedException. They can't be combined with UseObjectStreams, because the update keeps the source's layout.

Fonts are decoded through /ToUnicode maps; the standard, WinAnsi, MacRoman, PDFDoc and Symbol encodings with /Differences and glyph names; Type 3 fonts; and Type0 fonts with Identity or Unicode-based CMaps. Limits.

  • No OCR: text that is part of an image, or drawn as vector shapes, is not found.
  • Fonts without a /ToUnicode map that use Identity-H (common in CJK documents), or glyph names without a standard meaning, give U+FFFD; UnknownGlyphCount says how many.
  • Spaces and line breaks are inferred from positions, so they can differ from what a viewer's copy-and-paste gives.
  • Vertical text is read as horizontal text. Layout order reads multi-column pages across, line by line; content order usually follows the columns.
  • Widths of the standard 14 fonts are exact for ASCII; other characters use their base letter's width.

Watermarks and stamps

Pdf.Stamp (or IPdfStamper.StampAsync) adds text or an image to every page or a range of pages.

  • Text uses one of the standard 14 fonts, which every viewer has, so nothing is embedded. That limits text to the Windows-1252 (WinAnsi) characters; anything else is rejected with the characters listed. \n starts a new line.

Chaining operations

PdfPipeline runs several operations on one document in a row, for example a watermark and then a password. Each step reads the previous step's output, and nothing runs until you ask for the result with ToBytesAsync, ToStreamAsync, SaveAsync or RunAsync.

C#
byte[] pdf = await PdfPipeline.FromFile("report.pdf")
    .Watermark("CONFIDENTIAL")
    .RotatePages(90, "1-2")
    .EditInfo(i => i.Title = "Q3 report")
    .Protect(userPassword: "open-me", ownerPassword: "owner")
    .ToBytesAsync();
Console.WriteLine($"Encrypted: {Pdf.IsEncrypted(pdf)}, title: {Pdf.GetInfo(pdf, "open-me").Info!.Title}");

var result = await PdfPipeline.FromBytes(pdf)
    .WithPassword("owner")                 // opens the protected input
    .AddAttachment("data.csv", csvBytes)
    .Decrypt()
    .SaveAsync("report-final.pdf");
foreach (var step in result.Steps)
    Console.WriteLine($"{step.Name}: {step.Result}");

try
{
    await PdfPipeline.FromFile("report.pdf").Watermark("DRAFT").DeletePages("1-3").ToBytesAsync();
}
catch (Exception ex)
{
    Console.WriteLine($"{ex.Data["PdfPipelineStep"]} failed: {ex.GetType().Name}");
}
Output
Encrypted: True, title: Q3 report
AddAttachment: PdfEditResult { OutputVersion = 1.7, Algorithm = Aes256, Warnings = 0 }
Decrypt: PdfEditResult { OutputVersion = 1.7, Algorithm = None, Warnings = 0 }
2: DeletePages failed: ArgumentException

Steps

  • Built in: Stamp and Watermark, Protect, Decrypt, ChangeSecurity, EditInfo, RotatePages, DeletePages, Append (merge other documents after this one), Repair, Sanitize, AddAttachment and RemoveAttachment. Each takes the same options as the operation it runs, and most have a shorter overload, such as Watermark("DRAFT") or RotatePages(90, "odd").
  • Signing: PdfUtil.Signatures adds .Sign(options). Make it the last step: any later change invalidates the signature. Only unencrypted documents can be signed, so it cannot follow Protect.
  • Your own step: Then(name, step) gets the current PDF as a stream and writes the new one to another, with the password that currently opens it.
C#
var signed = await PdfPipeline.FromFile("contract.pdf")
    .Watermark("COPY")
    .EditInfo(i => i.Title = "Contract")
    .Sign(new PdfSignOptions { Certificate = certificate, Reason = "Approved" })   // using PdfUtil.Signatures
    .ToBytesAsync();
C#
.Then("Compress", async (input, output, password, ct) =>
{
    // read the current PDF from input, write the new one to output
    await input.CopyToAsync(output, ct);
    return null;                           // or a result object, shown in RunAsync's Steps
})

Passwords

WithPassword opens a protected input. After Protect or ChangeSecurity, the following steps open the result with the new owner password, and after Decrypt they need none, so you never repeat a password. A Password set on a step's own options wins. The pipeline never changes your options objects.

Put Protect at the end: the steps before it then work on an unencrypted document instead of each decrypting and re-encrypting it. Append returns an unprotected document.

Errors and output

  • Every step keeps its own self-verification. If a step fails, its exception is thrown with its original type, ex.Data["PdfPipelineStep"] says which step (for example "2: DeletePages"), and nothing is written.
  • SaveAsync replaces the file atomically, so the output can be the input file. RunAsync returns a PdfPipelineResult with the final PDF and each step's result and warnings.
  • Intermediate documents are kept in memory. A pipeline can run more than once; each run reads the input again.

Signing and verifying signatures

Signing and certificate encryption are in a separate package, PdfUtil.Signatures, because they depend on System.Security.Cryptography.Pkcs. Add it with dotnet add package PdfUtil.Signatures, and register it with services.AddPdfUtilSignatures().

C#
IPdfSigner signer = new PdfSigner();
await signer.SignFileAsync("report.pdf", "report-signed.pdf", new PdfSignOptions
{
    Certificate = new X509Certificate2("signer.pfx", pfxPassword),
    Reason = "Approved",
    Appearance = new PdfSignatureAppearance { Page = 1, Bounds = new PdfRectangle(36, 36, 236, 96) },
});

await using var signed = File.OpenRead("report-signed.pdf");
var verification = await signer.VerifyAsync(signed);
foreach (var signature in verification.Signatures)
    Console.WriteLine($"{signature.FieldName}: {(signature.IsValid ? "valid" : "INVALID")}, signed by {signature.SignerName}, {signature.SubFilter}, covers whole file: {signature.CoversWholeFile}");
Output
Signature1: valid, signed by Jane Signer, ETSI.CAdES.detached, covers whole file: True

Signing

  • Format: PAdES baseline B-B (ETSI.CAdES.detached) with SHA-256, SHA-384 or SHA-512, RSA or ECDSA keys, and the ESS signing-certificate-v2 attribute. With TimestampServer, an RFC 3161 timestamp is added (B-T); pass your own HttpClient in TimestampHttpClient to control proxies and timeouts.
  • Visible or not: without Appearance the signature is invisible. With it, a box shows who signed and when (or your own Text), on the page as displayed.
  • Fields: set FieldName to sign an existing empty signature field; otherwise a new field is added.
  • Earlier signatures stay valid: the signature is always appended as an incremental update. Only unencrypted documents can be signed.
  • Keys elsewhere: a key that isn't attached to the certificate (from a hardware module or key vault) goes in PrivateKey.
  • Verified: the signed file is checked (digest and signature) before you get it.

Verifying

VerifyAsync checks each signature and document timestamp: the digest of the signed bytes, the CMS signature, the signing and timestamp times, the revision it signed, whether later revisions changed the document and how (for example "signatures added" or "annotations added or changed"). Set ChainPolicy to also validate the certificate chain against your trust anchors and revocation settings. Supported formats: adbe.pkcs7.detached, ETSI.CAdES.detached, adbe.pkcs7.sha1 and ETSI.RFC3161 document timestamps.

Rewriting breaks signatures. Every operation that rewrites a document (protection, sanitize, repair, ...) invalidates its signatures and warns you. To change a signed document, use the incremental save mode (Smaller files and incremental saves).

Certificate encryption

Instead of a password, a document can be encrypted for the certificates of its recipients. Each recipient opens it with their own private key, and each can have different permissions.

C#
IPdfCertificateSecurity security = new PdfCertificateSecurity();
await security.ProtectFileAsync("report.pdf", "report-for-alice.pdf", new PdfCertificateProtectionOptions

});

{
    Certificate = aliceCertificate,
    PrivateKey = aliceKey,                 // or a certificate with its private key attached
});

Encrypted after decrypting: False
  • Format: /Adobe.PubSec with adbe.pkcs7.s5, AES-256 (default) or AES-128 crypt filters. Each recipient's key is in a CMS envelope (AES-256) for their RSA certificate.
  • Opening: InspectAsync with a recipient's certificate reads everything; DecryptAsync writes an unprotected copy. Removing protection needs a recipient with every permission, or AllowRestrictedRecipient.
  • Without the package, Pdf.GetInfo and Pdf.VerifyPassword report such documents (RequiresCertificate, the recipient count) instead of failing.

Reader support. Certificate-encrypted files open in Adobe Acrobat and Reader with the recipient's certificate installed. Browsers (pdf.js, PDFium) and Apple Preview don't support them.

Two layouts

  • Reflow (default) rebuilds the structure: paragraphs from line spacing and indentation, headings from larger or bold text, bulleted and numbered lists, reading order across columns. The result reads well on any screen and is easy to restyle.
  • Fixed keeps each page as it looks: a box per page with every text run and image at its position. Text stays selectable and searchable.

Images and output

  • Images: inside the HTML as data URIs (default, the only choice for stream output), in a folder next to the HTML file (SeparateFiles; the folder is replaced as a whole), or left out (None).
  • Checked before it is returned: the HTML is well-formed XML as well as HTML5, ids are unique, internal links and images resolve, and it contains no scripts, event handlers or unsafe links. Xhtml = true adds an XML declaration for XML tool chains.
  • Safe by design: nothing is fetched from the network, JavaScript and launch actions in the PDF are dropped with a warning, and PdfConversionLimits caps image sizes and output elements.

PDF to Word

PDF to Word uses the same structure analysis as reflowable HTML and writes the result as a Word document (DOCX). The package is written by PdfUtil itself: no Office installation or third-party library is involved.

var result = await converter.ConvertToDocxFileAsync("article.pdf", "article.docx", new PdfToDocxOptions
{
    PageBreaks = false,     // true: each PDF page starts a new page in Word
});
Console.WriteLine(result);
Output
PdfToDocxResult { Pages = 1, Paragraphs = 5, Headings = 2, Lists = 1, Tables = 0, Images = 1, Bytes = 4519 }

HTML to PDF

PdfUtil parses HTML and CSS and lays out the pages itself; no browser or other tool is involved.

C#
IPdfConverter converter = new PdfConverter();
var options = new HtmlToPdfOptions
{
    PageSize = PdfPageSize.A4,
    FooterHtml = "<p style='text-align:center; font-size:9pt'>Page {page} of {pages}</p>",
    ResourceResolver = HtmlResources.FromDirectory("site"),   // CSS and images next to the page
};
options.Fonts.Add(new PdfFontSource(File.ReadAllBytes("fonts/unicode.ttf"), "Body"));
var result = await converter.ConvertFromHtmlFileAsync("site/report.html", "report-from-html.pdf", options);
Console.WriteLine(result);
foreach (var warning in result.Warnings) Console.WriteLine("  " + warning);
Output
HtmlToPdfResult { Pages = 1, Fonts = 1, Images = 0, Links = 0, Bytes = 21095 }
  Font Body has no bold face; the regular face is emboldened or slanted instead.
  • Pages: PageSize and Margins, or CSS @page { size; margin }. HeaderHtml and FooterHtml repeat on every page; {page} and {pages} become the page number and count.
  • Fonts: text without a TrueType font uses the standard PDF fonts, which cover Western European text. For anything else, supply fonts (Fonts, FontDirectories, UseSystemFonts, or CSS @font-face): they are embedded as subsets with a Unicode map, chosen character by character, so text stays searchable and copyable.
  • Resources: style sheets, images and fonts are loaded only through ResourceResolver. HtmlResources.FromDirectory serves one folder and refuses paths outside it; data: URIs always work. Nothing is ever fetched from the network by PdfUtil.
  • Checked: the PDF is read back before it is returned, and the text a reader extracts must equal the text that was laid out. Protection protects it in the same call.

Passwords

Passwords are never plain arguments: arguments are visible to other users in process lists and end up in shell history. Each password the command needs comes from:

  • an environment variable you name: --password-env NAME, --owner-password-env NAME, --user-password-env NAME, --certificate-password-env NAME;
  • standard input with --password-stdin: one line per password, in the order the command's help shows (for protect: user, then owner);
  • a hidden prompt, when the tool runs in a terminal and nothing else gave the password. Encrypted inputs are detected and asked for.

PDF/A and signatures

PDF/A

PDF/A, the archival standard, forbids encryption. PdfUtil detects PDF/A from the pdfaid entries in the XMP metadata. With the default PdfAPolicy.Throw, protection throws PdfComplianceException. With PdfAPolicy.Proceed the file is encrypted anyway and a warning is added; it is then no longer a valid PDF/A file.

Digital signatures

Protection rewrites the file, which invalidates any existing digital signatures. PdfUtil warns when the input is signed. Signature values (/Contents) are never encrypted, as the specification requires.

Metadata encryption

By default the XMP metadata is encrypted along with everything else. Set EncryptMetadata = false (AES only) to leave it readable without a password, for example so that search indexers can read it.

Security and limits

  • Passwords are never logged, cached, or included in exception messages or ToString() output.
  • Password and key buffers are zeroed after use, and password hashes are compared in constant time.
  • Hostile-input limits protect you from malicious files. You can configure the file size, object count, nesting depth, decompressed stream size (zip-bomb protection) and the number of cross-reference sections. Loops in the file structure are detected.
  • Unexpected failures inside the parser surface as PdfCorruptException, never as crashes with unrelated exception types.

FAQ and troubleshooting

My password is rejected with PdfPasswordEncodingException.

It contains characters that some viewers would encode differently, so the protected file wouldn't open everywhere. Choose a password without those characters, switch to Aes256 (which accepts many more scripts), or set PasswordPolicy = Specification if you only target specification-compliant readers. See Password rules.

Why did the PDF version change?

Each algorithm needs a minimum version: 1.4 for RC4, 1.6 for AES-128, 1.7 for AES-256. The version is raised to that minimum when needed, and never lowered.

Why is the protected file larger, or smaller?

AES adds 16 to 32 bytes per string and stream, and strings are written as hex. Files can also shrink, because unreferenced objects and linearization data are dropped and object streams are written as plain objects.

Fast web view is gone after protecting.

That's intentional. Linearization hints cannot survive a rewrite, and stale hints break browsers.

A colleague's old reader can't open the file.

Readers from before about 2008 don't support AES-256. Protect with Algorithm = PdfEncryptionAlgorithm.Aes128.

Can I remove protection?

Yes, with the owner password: Pdf.Decrypt. See Removing and changing protection.

The input is digitally signed.

Protection works, but it invalidates the signatures, and a warning tells you so. Sign after protecting if you need both.

A viewer says the file is damaged. Can PdfUtil fix it?

Often, yes. Run Pdf.Validate to see what is wrong, then Pdf.Repair to write a clean copy. The result lists every repair, and says whether pages may be missing. See Repairing a damaged file.

How do I make sure a PDF contains no JavaScript?

Pdf.Inspect(path).HasJavaScript tells you; Pdf.Sanitize with the default options removes it. See Removing scripts and other content.

How do I make files smaller?

Set Write = new PdfWriteOptions { UseObjectStreams = true }. Files often shrink by a third or more, but need a reader from 2003 or later. See Smaller files and incremental saves.

Can I change a signed document without breaking the signature?

Use SaveMode = PdfSaveMode.Incremental with EditInfo or the attachment methods. The signed bytes stay intact; viewers will show that the document was changed after signing.

Why does an attachment have two file names?

/UF holds the full Unicode name, and /F an ASCII version for old readers, with other characters replaced by _. Modern viewers show /UF.
